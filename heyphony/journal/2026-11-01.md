# 2026-11-01

## decided

- the number lives on the **host**, registered once. a second registration is a race, a secret in a burnable guest has to be reissued every spawn, and a number that only rings while a guest is up is dead in the idle case that matters most.
- **baresip** is the host client, because `ctrl_tcp` is a json socket rather than a screen to scrape. pjsua lost on weight; the verdict is stored as data with its reasoning so it does not get relitigated from vibes.
- receiving is the product and sending is narrow. bulk outbound and otp are refused by nature rather than deferred, because a did is voip and no dashboard fee changes the classification.
- provisioning stops **before the money step**. everything up to the purchase is scriptable and tested; the purchase stays a person's act, for every provider, including the one whose api could do it.
- the readme explains, [theidea](../theidea/) argues, and this journal records. three jobs, three places.

## built

- ten providers as data, each with `text_style` and `sip_style`, seven of them able to receive a text and three voice only.
- the hooks layer: what to paste per provider, and the exact api call for the ones that have one, with credentials missing reported rather than half-configured.
- anveo's whole chain: areas with stock and rate plan prices per area code, the order call prepared, and `DID.UPDATE` to arm `SMS_URL` on a number you own. the signed request is computed here and pinned against their published vector.
- the launcher: caught texts and carrier voicemail as one thread with a person, parsed out of forwarded provider email rather than typed in by hand.
- the setup plan now carries voicemail and catching as first class steps, so "connect the sip client" is no longer mistaken for "the number works".

## refused

- wiring a payment rail to the provisioning cli. anveo would happily order and bill in one call, and that is exactly why it waits: an agent that can spend money is a different product with a different consent story.
- sending sms from the launcher's reply box. the thread view drafts, shows the route, and says what is missing, because a send is the half with consequences and half a send path is worse than none.
- storing the owner as just another contact. see [recognica](../../comms/recognica/readme.md): who the agent serves is not a tag on a card, it is a different shelf.

## unproven

- no number has received a real text through this catcher yet. every provider in the table says `verified: false` for that reason.
- no call has been placed. the log reader is tested against the client's own sqlite schema, not against a live call.
- no voicemail email has been parsed from a real carrier mailbox; the shapes were built from published formats and need one real specimen each before anyone trusts the thread view.
- the licence question is open, not answered, and depends on whether linphone ends up in the code path or only in the config format.
